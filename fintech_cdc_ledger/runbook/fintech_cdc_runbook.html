Fraud velocity alerts — Q2

Ran clean · 0 alerts — explained, not glossed over

Which accounts moved 80%+ of their starting balance out within any rolling 15-minute window (not a clock-aligned bucket)? A rangeBetween(-900, 0) window over epoch-seconds, per the brief — not rowsBetween, not a tumbling window().

Real result, and the real reason for it

MetricValue
Alerts found0
Accounts with exactly 1 transaction26,412 / 26,412 — 100%
Accounts with 2+ transactions0

This rule can only fire when an account has at least two transactions close together, so it can compare "money that just left" against "what they had before." Checked directly: every single account in this dataset has exactly one transaction, ever. There is structurally never a second transaction to compare against — so 0 alerts is the correct, expected answer for this dataset, not a sign the rule is broken.

Honest limitations (as required)

  • Why this happened here: the harness pulls real PaySim rows by real customer ID, and PaySim's customer IDs are almost all one-time-use across the dataset — so no account in this 20-day slice ever transacts twice.
  • Pattern this rule can never see #1 — patient draining: money moved out slowly across many hours or days, always staying under 80% in any single 15-minute window, evades this rule by design.
  • Pattern this rule can never see #2 — first-transaction fraud: a single large transaction with no prior balance on record looks identical to a legitimate first-time transfer — there's no "before" state to compare against.
  • Not done: cross-checking against PaySim's real isFraud column for precision/recall — that field was never carried through bronze → silver in this pipeline, so it isn't available to join against here. A real gap, not a hidden one.

The materialized view is about 5x faster than either path that reads the real files. At this data size (26,412 ledger rows, a 61-row result) most of the 1.4-1.5 second cost in the other two paths is fixed per-query planning overhead, not actual data volume — the gap would grow much larger at real production scale, where scanning millions of rows every time gets expensive fast.

The tradeoff (required, not optional)

The materialized view was created with AUTO REFRESH NO — it does not update itself. Every minute that passes after a REFRESH MATERIALIZED VIEW, its numbers drift further from the live ledger. A dashboard reading it is fast but shows a snapshot, not the current truth, until someone (or something) refreshes it again — and each refresh re-runs the full aggregation, costing roughly the same ~1.5 seconds the Spectrum path costs on its own.

Recommendation for a dashboard refreshing every 5 minutes: the materialized view, refreshed on a 5-minute schedule to match. A 5-minute-stale executive summary is an acceptable tradeoff for 5x the speed on every read in between — but if the dashboard needed to reflect a MERGE that happened 10 seconds ago (an auditor mid-investigation, say), Spectrum's always-current-but-slower path is the correct choice instead.
